# Kubecrate v0.12.0 release notes

## Summary

This release moves the cert-manager platform service chart `cert-manager` from v1.20.5 to v1.21.3 in `platform-services/cert-manager/base/`. It is step 5 of the one-minor-at-a-time path to v1.21.3. The Vanilla composition paths and values are unchanged.

## Breaking change

No Kubecrate path or values change. See the upstream upgrade notes for 1.20 to 1.21 (https://cert-manager.io/docs/releases/upgrading/upgrading-1.20-1.21/) and the upstream v1.21.0 release notes (https://github.com/cert-manager/cert-manager/releases/tag/v1.21.0). Three upstream changes to note:

- The chart no longer creates the default `Role` and `RoleBinding` for `serviceaccounts/token` (`create`) that let the controller create tokens for its own ServiceAccount. A consumer whose Issuer authenticates with a ServiceAccount token (for example Vault Kubernetes auth, or Route53) through `serviceAccountRef.name` pointing at the controller ServiceAccount creates that `Role` and `RoleBinding` itself, or moves to a dedicated ServiceAccount (upstream's recommendation). Kubecrate's defaults are not affected in function: the chart creates the Role and RoleBinding `cert-manager-tokenrequest` by default (`serviceAccount.create: true`, which `helm-values.yaml` does not change), so Helm removes the two objects on this upgrade, but Kubecrate ships no Issuer or ClusterIssuer that uses them.
- The `prometheus.servicemonitor` values `targetPort` and `path` and the `prometheus.podmonitor` value `path` are removed (the path is always `/metrics`, the port always `http-metrics`). A values override that still sets one fails the chart's schema check on upgrade. Kubecrate's defaults are not affected: `helm-values.yaml` sets no `prometheus` values. A consumer that sets any of the three removes them first.
- The controller Service's metrics port is renamed from `tcp-prometheus-servicemonitor` to `http-metrics` (port 9402 is unchanged). Kubecrate's defaults get the renamed port: the chart creates this Service by default (`prometheus.enabled: true`, no PodMonitor), and Kubecrate ships no ServiceMonitor, PodMonitor or scrape config that names the port. The pods keep their `prometheus.io/scrape`, `prometheus.io/path` and `prometheus.io/port` annotations. A consumer that scrapes by port name changes its scrape config to `http-metrics`; one that scrapes by pod annotation (tenant-02 does) is not affected.

Other behaviour changes in the upstream v1.21.0 to v1.21.3 notes that can reach a consumer. None changes Kubecrate's defaults, because Kubecrate ships no Issuer, ClusterIssuer or Certificate and sets no feature gate, controller config or `securityContext`:

- The aggregated `cert-manager-edit` ClusterRole no longer grants `create` on Challenges or `create`, `patch` and `update` on Orders (upstream advisory GHSA-8rvj-mm4h-c258). This already shipped in `v0.10.0` (chart v1.19.6), so this tag does not change it again. A consumer whose users or tools create or change Challenges or Orders directly needs its own Role, as the `v0.10.0` notes say.
- Issuers and ClusterIssuers validate the Secrets of ACME DNS-01 solvers before they report Ready, so an Issuer whose solver Secret is missing reports `Ready: False` with reason `InvalidSolver`. v1.21.0 did not recover when the Secret was created later; v1.21.1 fixes this.
- The Vault issuer webhook rejects `..` path segments in `spec.vault.path` and the auth mount paths. A namespaced Vault `Issuer` no longer uses the controller's ambient AWS credentials for the new AWS IAM auth unless `--issuer-ambient-credentials` is set (v1.21.2).
- ACME and Vault response bodies are no longer copied into Issuer, Challenge and Event status messages (v1.21.2). A consumer that parses those messages finds the HTTP status code or the bounded ACME problem document instead; the full error stays in the controller logs.
- The validating webhook now also enforces validation for equivalent-converted requests on non-v1 API versions (v1.21.2).
- The new `renewal` field on Certificate and the `ACMEUseARI` feature gate are opt-in. The `ACMEUseARI` gate is off by default and ARI is experimental. v1.21.0 crash-looped the controller for a Certificate with `renewal.policy: Disabled`; v1.21.1 fixes this.
- The container images no longer trust the "emSign ECC Root CA - G3" root certificate, and Go 1.26.10 rejects certificate chains through the compromised eMudhra intermediates (v1.21.3, https://cert-manager.io/docs/trust/trust-manager/#emudhra-compromise). A consumer whose ACME or Vault endpoint chains through that CA must switch CA.
- The controller's `requestmanager` and `issuing` controllers only use the Secret named by `status.nextPrivateKeySecretName` when it carries the `cert-manager.io/next-private-key` label and the Certificate owns it (v1.21.3).
- Deprecated, with the old setting still working: `enableGatewayAPI` and `enableGatewayAPIListenerSet` in the controller configuration (now `gatewayAPI.enabled` and `gatewayAPI.enableListenerSet`), and the `ServerSideApply` feature gate (cainjector always uses server-side apply). `CAInjectorMerging` is GA.

## Details

- The 6 CRDs (`certificates`, `certificaterequests`, `issuers` and `clusterissuers` in `cert-manager.io`; `challenges` and `orders` in `acme.cert-manager.io`) serve and store only `v1` in both v1.20.5 and v1.21.3. No version, field or CRD is removed in v1.21.3.
- The v1.21.3 schemas add these optional fields. Description-only changes are ignored.
  - `certificates`: `spec.renewal` (`policy`, enum `RenewBefore` or `Disabled`; `windows[]` with `cron`, `timezone` and `windowDuration`) and `status.acme.ari` (`certID`, `explanationURL`, `lastChecked`, `lastError`, `nextCheck` and `suggestedWindow` with `start` and `end`).
  - `issuers` and `clusterissuers`: `spec.acme.solvers[].waitInsteadOfSelfCheck`, `spec.vault.auth.aws` (`role`, `iamRoleArn`, `mountPath`, `region`, `vaultHeaderValue` and `serviceAccountRef` with `name` and `audiences`) and `spec.venafi.ngts` (`tsgID`, `credentialsRef`, `tokenEndpoint` and `url`).
  - `challenges`: `spec.solver.waitInsteadOfSelfCheck` and `status.presentedAt`.
  - `orders`: `spec.replaces`.
  - `certificaterequests`: no field added.
- Two existing schema entries change, with no stored object affected:
  - the `spec.keystores.pkcs12.profile` enum of `certificates` gains `Modern2026`;
  - `spec.venafi` of `issuers` and `clusterissuers` gains the validation rule that exactly one of `tpp`, `cloud` or `ngts` is configured.
- The CRDs are chart templates (`crds.enabled: true`) with `helm.sh/resource-policy: keep`.
- `helm-values.yaml` is unchanged; every key it sets exists in v1.21.3.
- Nothing else in the repository changes.

## Upgrade guidance

1. Be on Kubecrate `v0.11.0` first. Upstream recommends upgrading one minor version at a time (https://cert-manager.io/docs/installation/upgrade/).
2. Update the consumer repository's Kubecrate source tag to `v0.12.0`.
3. Run the consumer repository's render validation.
4. Reconcile.
5. Verify the `cert-manager` `HelmRelease` is Ready on chart v1.21.3, every Certificate, Issuer and ClusterIssuer is Ready, and each Certificate's `status.revision` is unchanged.

A consumer on a Kubecrate tag older than `v0.11.0` (cert-manager older than v1.20) adopts, in order, each tag of `v0.8.0`, `v0.9.0`, `v0.10.0`, `v0.11.0` and `v0.12.0` that is newer than its current tag, and reconciles and checks each one (steps 2 to 5 above, with that tag's chart version) before the next. The one-at-a-time order is because upstream supports upgrading one minor version at a time (https://cert-manager.io/docs/installation/upgrade/). A consumer older than `v0.7.0` (for example tenant-01 on `v0.4.0`) first moves to `v0.7.0` along the release notes of each tag up to it, because the `v0.8.0` notes start from `v0.7.0`.

## Rollback

Rollback by restoring the previous exact Kubecrate tag `v0.11.0` in the consumer repository. Helm re-renders the CRD templates on the downgrade (`helm.sh/resource-policy: keep` only stops their deletion). Both versions serve only `v1`, so no stored object changes its version. The v1.21.3 CRDs add the fields listed in Details: `spec.renewal` and `status.acme.ari` on Certificates, `waitInsteadOfSelfCheck`, `vault.auth.aws` and `venafi.ngts` on Issuers and ClusterIssuers, `waitInsteadOfSelfCheck` and `status.presentedAt` on Challenges, and `spec.replaces` on Orders. After a rollback to `v0.11.0` the API server prunes them from stored objects, so a consumer that set them loses them, and `Modern2026` is no longer a valid `pkcs12.profile`. A consumer that set `renewal.policy: Disabled` loses that policy and its Certificates renew again.

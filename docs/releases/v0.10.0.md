# Kubecrate v0.10.0 release notes

## Summary

This release moves the cert-manager platform service chart `cert-manager` from v1.18.6 to v1.19.6 in `platform-services/cert-manager/base/`. It is step 3 of the one-minor-at-a-time path to v1.21.3. The Vanilla composition paths and values are unchanged.

## Breaking change

No Kubecrate path or values change. See the upstream upgrade notes for 1.18 to 1.19 (https://cert-manager.io/docs/releases/upgrading/upgrading-1.18-1.19/). Three upstream changes to note:

- Never pin chart v1.19.0. It reissues every Certificate whose `issuerRef` omits `group` or `kind` (https://github.com/cert-manager/cert-manager/issues/8158, fixed in v1.19.1). Kubecrate ships no Certificate, Issuer or ClusterIssuer and pins v1.19.6, so its defaults are not affected. This only affects consumers that pin v1.19.0 and have Certificates with those fields omitted.
- The ACME client metrics `certmanager_acme_client_request_count` and `certmanager_acme_client_request_duration_seconds` rename the label `path` to `action` to bound cardinality. Kubecrate's defaults are not affected because it ships no dashboard or alert for these metrics. A consumer dashboard or alert that uses `path` must change to `action`.
- From v1.19.6, the aggregated `cert-manager-edit` ClusterRole no longer grants `create` on Challenges or `create`, `patch` and `update` on Orders (chart `templates/rbac.yaml` in v1.18.6 and v1.19.6). Challenges and Orders are internal to the ACME flow and are not meant to be created or changed by users. The chart ships `cert-manager-edit` and by default aggregates it into the cluster's `edit` and `admin` roles (`global.rbac.aggregateClusterRoles: true`), so users bound to `edit` or `admin` lose those verbs (upstream advisory GHSA-8rvj-mm4h-c258). Kubecrate's defaults are not affected because nothing Kubecrate ships creates or changes Challenges or Orders. A consumer whose users or tools create or change them directly needs its own Role.

## Details

- The 6 CRDs (`certificates`, `certificaterequests`, `issuers` and `clusterissuers` in `cert-manager.io`; `challenges` and `orders` in `acme.cert-manager.io`) serve and store only `v1` in both v1.18.6 and v1.19.6.
- The CRDs are chart templates (`crds.enabled: true`) with `helm.sh/resource-policy: keep`.
- `helm-values.yaml` is unchanged.
- Nothing else in the repository changes.

## Upgrade guidance

1. Be on Kubecrate `v0.9.0` first. Upstream recommends upgrading one minor version at a time (https://cert-manager.io/docs/installation/upgrade/).
2. Update the consumer repository's Kubecrate source tag to `v0.10.0`.
3. Run the consumer repository's render validation.
4. Reconcile.
5. Verify the `cert-manager` `HelmRelease` is Ready on chart v1.19.6, every Certificate, Issuer and ClusterIssuer is Ready, and each Certificate's `status.revision` is unchanged.

## Rollback

Rollback by restoring the previous exact Kubecrate tag `v0.9.0` in the consumer repository. Helm re-renders the CRD templates on the downgrade (`helm.sh/resource-policy: keep` only stops their deletion). Both versions serve only `v1`, so no stored object changes its version. The v1.19.6 Issuer and ClusterIssuer CRDs add fields (for example RFC2136 `protocol` and the ACME HTTP01 solver's `podTemplate.spec.resources`). After a rollback to `v0.9.0` the API server prunes such fields from stored objects, so a consumer that set them loses them.
